# 문장 유형 조사 — 대본 문장 기준을 자료에서 뽑기 (2026-10-03)

브랜치 `cloud/sentence-types-1003`. 팀장이 낸 4분류([정보없음]·[숫자나열]·[반복면책]·[포장만])와 '알찬 문장 3조건'(① 시청자가 몰랐던 사실 ② 왜 중요한지 ③ 무엇을 확인·할지)은 규칙으로 쓰지 않았다. 가설로만 두고 숫자로 시험했다.

## 1. 요약

- 경쟁 롱폼 받아쓰기 17편에서 100문장, 우리 대본 5편(A-1·E-1·D-1·E-2·N-1)의 say에서 100문장을 고정 시드(1003)로 뽑았다. 출처를 가리고 섞은 목록에서 문장마다 '시청자가 이 문장에서 얻는 것'을 한 줄로 적었다. 그 메모를 묶어 **유형 13개**를 만들었다.
- 경쟁과 우리가 확실히 다른 것은 세 가지다.
  1. **여러 값 나열**: 경쟁 2%, 우리 16% (p=0.0008). 숫자가 3개 이상 든 문장은 경쟁 1%, 우리 21%다.
  2. **풀이**(뜻 풀이+이유+판단·전망): 경쟁 28%, 우리 12% (p=0.0075).
  3. **근거 밝힘+선 긋기**(가정·출처·한계·면책을 말로 함): 경쟁 1%, 우리 14% (p=0.0006).
- 차이가 없는 것: 사실 하나, 안내·예고, 질문, 할 일, 규칙·구조.
- 가설 판정: [숫자나열] 맞음, [반복면책] 맞음, [정보없음] 틀림, [포장만] 틀림. 3조건은 '한 문장에 셋 다'가 틀림(경쟁 0/100), ① 틀림, ② 판단 불가(방향은 맞음), ③ 판단 불가.
- 같은 채널 안에서 조회수 높은 편과 낮은 편 비교는 **확인 안 함**이다. 받아쓰기 17편이 모두 다른 채널이라서다.

## 3. 코딩 방법

1. 뽑은 200문장에 섞은 번호(S001~S200)를 붙이고, 출처를 뺀 `blind.tsv`만 보고 코딩했다.
2. 문장마다 '시청자가 이 문장에서 얻는 것'을 한 줄 메모로 적었다(`blind_codes.tsv`).
3. 메모를 비슷한 것끼리 묶어 유형을 만들었다. 유형 이름은 문장 속 말(예: "~라는 뜻이죠", "~보겠습니다", "말하지 않습니다")에서 따왔다.
4. 같은 메모에 3조건 표시(c1 새 사실, c2 왜 중요·무슨 뜻, c3 확인·할 일)를 0/1로 따로 달았다. 숫자 개수는 코드가 센다(아라비아 숫자 덩어리, 한글 수사 "세 배"는 안 셈).
5. 다 적은 뒤에 `samples.tsv`와 합쳐 `codes.tsv`를 만들었다.

한계: 코더가 한 명(이 세션)이다. 두 번째 코더와의 일치도는 확인 안 함. 출처를 가려도 '제피큐', '파이어맵', 반말 진행처럼 말투로 출처가 짐작되는 문장이 있었다. 뽑기 뒤 `samples.tsv` 맨 앞 4줄을 형식 확인용으로 한 번 열어 봤다(S001~S004).

### 같은 채널 안 조회수 높은 편·낮은 편

**확인 안 함.** 받아쓰기 17편이 17개 채널에 하나씩이라 같은 채널 안에서 비교할 수 없다. 더 받으려면 같은 채널 영상 받아쓰기를 새로 떠야 하는데, 이번에는 저장소 자료만 썼다.

보조로, 채널을 섞은 채 경쟁 표본을 조회수 10만 이상(70문장)과 미만(30문장)으로 나눠 봤다. 어느 묶음도 차이가 없었다(값 전달 40% 대 37% p=0.83, 풀이 24% 대 37% p=0.23, 사람 말 19% 대 7% p=0.22). 채널·주제가 섞여 있어 조회수 효과로 읽을 수 없다.

## 8. 줄 검토 적용 방법

줄 검토 담당(다른 에이전트)이 대본 줄마다 이렇게 쓴다.

1. **문장마다 유형 하나를 붙인다.** 13개 중 하나. 두 개에 걸치면 '시청자가 가장 크게 얻는 것' 하나만 고른다. 고르는 순서:
   질문(물음표·"~냐") → 안내·예고("~보겠습니다", "첫째,", "정리해 볼게요") → 선 긋기("말하지 않습니다", "~뜻은 아닙니다", "사람마다 다릅니다") → 근거 밝힘("~로 가정", "~에서 계산해 봤어요", 출처 이름) → 할 일 → 여러 값 나열(값·이름 2개 이상이 각각 새로 나옴) → 뜻 풀이·이유·판단·전망 → 규칙·구조 → 사실 하나 → 장면·이야기 → 강조·맞장구.
2. **바로 고칠 유형**
   - 여러 값 나열 → 고쳐 쓴다. 말에는 반올림한 숫자 하나만 남기고 나머지 값은 [자막]·화면으로 뺀다. 필요하면 두 문장으로 나누고 둘째 문장을 뜻 풀이로 쓴다.
   - 선 긋기 → 끝 면책 한 문장만 남기고 지운다. 한계가 결론을 바꾸는 경우만 남기되 뜻 풀이 꼴("그러니 1년 치만 보고 판단하면 안 됩니다")로 다시 쓴다.
   - 근거 밝힘 → 화면 출처·설명란으로 옮긴다. 가정이 답을 바꾸는 계산 앞에서는 짧은 한 문장만 남긴다.
3. **더할 것**: 사실 하나나 여러 값 나열 뒤 3문장 안에 풀이(뜻 풀이·이유·판단·전망)가 없으면 한 문장을 더한다. 예: "~라는 뜻이에요", "이렇게 보시면 돼요", "~라서 그렇습니다".
4. **건드리지 않을 유형**: 안내·예고, 질문, 장면·이야기, 강조·맞장구, 사실 하나, 규칙·구조, 할 일. 이것들은 지울 근거가 없다. 경쟁은 이것들을 우리와 같거나 더 많이 쓴다.
5. **한 편 끝나면 비율을 센다.** 목표: 여러 값 나열 ≤7%, 숫자 3개 이상 문장 ≤5%, 숫자 2개 이상 문장 ≤19%, 풀이 ≥20%, 근거 밝힘+선 긋기 ≤5%. 숫자 개수는 `sentencetypes.count_numbers()`로 센다.
6. 검토 결과 줄에는 `[유형] 고칠 것 / 그대로`를 함께 적는다. 예: `[여러 값 나열] 고침: 81만원만 말로, 6만 7,860원은 [자막]`.

## 9. 확인 안 함

- 같은 채널 안 조회수 높은 편·낮은 편 유형 비교(채널마다 받아쓰기 1편뿐).
- 두 번째 코더와의 일치도. 코더 1명이고, 말투로 출처가 짐작되는 문장이 있었다.
- 팀장 4분류·3조건의 원래 정의(저장소에서 못 찾음, 이름 뜻대로 정의함).
- `loop/subs/*.json3` 사람 자막(저장소에 없음). 경쟁 문장은 제미나이 받아쓰기라 실제 말과 다를 수 있다. 문장부호도 받아쓰기가 붙인 것이다.
- 조회수는 저장소 JSON 값(9/30~10/3에 받은 값). 오늘 다시 열어 보지 않았다.
- -Yh53SjCAiw(1.4분), tVaz2qoAySM(2.0분)은 길이가 쇼츠에 가깝다. 지시대로 17편 모두 넣었다. 두 편을 빼고 다시 센 결과는 확인 안 함.
- 유형 비율과 조회수 사이의 인과(이 조사는 경쟁과 우리의 차이만 보여 준다).
- 묶음(풀이·근거·선 긋기 등)은 코딩 뒤에 정한 것이다. 미리 정한 가설 검정이 아니다.
