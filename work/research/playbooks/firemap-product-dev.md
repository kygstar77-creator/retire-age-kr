# 제품 개발(firemap-product-dev) 교본

## 경쟁 1등 사례
- 사람인 연봉계산기: 기본값(비과세 20만·가족 1·자녀 0)을 채워 둬서 연봉 한 칸이면 공제 6줄이 바로 나온다. 계산 뒤 주소가 ?salary=4000으로 바뀌고 제목도 '연봉 4000만원 실수령액'이 된다.
- 네이버 '임금계산기' 위젯: 검색 결과 맨 위에서 시급·연봉·퇴직금·실업급여·월급 탭으로 먼저 답한다. 그래서 검색수가 곧 클릭 수요는 아니다. 약점도 있다. 스스로 '간이세액표(2024년 3월) 기준'이라고 적는다(10/1 실측).

## 잘된 우리 사례
- 연봉 계산기(10/1): 간이세액표를 법령 API 별표내용에서 646구간 그대로 옮겼다. 손입력이 0이라 오타 위험도 0이다. 그 뒤 세 포털 결과와 줄마다 대조했다.
- 경계 대조가 버그 2개를 잡았다. 정확히 1,000만원인 경계와, 소수 요율을 곱할 때 생기는 10원 오차다. 평범한 예시 5건은 둘 다 통과했다.

## 실패 사례
- 퇴직금 대조가 prebuild에 안 걸려 있었다(9/30 발견). 대조 스크립트를 만들면 그 자리에서 package.json prebuild에 건다.
- 기본값을 앱 기본값(생활비 300만)에서 그대로 가져왔다. 그러자 기본 화면의 은퇴 카드가 '저축 0원'이 됐다. 이긴다고 내세운 점이 기본 화면에서 막히는지 꼭 본다.
- 문서에 시각을 짐작으로 '01시'라고 적었다. 실제는 00:19였다. 기록 전에 `date`를 찍는다.

## 체크리스트(새 계산기)
1. kwvol로 검색수를 잰다. 네이버 1페이지는 curl(모바일 UA)로 m.search.naver.com을 받아 본다. 브라우저 두 개는 막혀도 curl은 받아진다.
2. 법 원문은 lawtext.py로, 별표는 법령 API 별표내용으로 받는다. 부칙(연도별 요율)도 따로 찾는다. 본문만 보면 최종값(13%)을 현재값으로 착각한다.
3. 요율은 정수 분수로 곱한다. 끝수 처리를 조문으로 확인한다.
4. 손검산은 파이썬 Fraction으로 따로 한다. 경계 대조(구간 시작·끝·정확히 경계값)를 넣는다. prebuild에 건다.
5. 경쟁 3곳의 같은 입력 결과를 줄마다 대조한다.
6. toolPages body는 화면 문장 그대로 쓴다. smoke가 검사한다.
7. 참모 3명(사용자·법·레드팀)을 병렬로 부른다. 기본 화면이 막다른 길인지 직접 본다.
8. 큰 표는 React.lazy로 따로 불러온다.
