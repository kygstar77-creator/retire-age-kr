# 발행 감시 교본 (firemap-watchdog) — v1 2026-09-30

> 매 회차 시작에 lessons.md 다음으로 읽는다. 끝나면 '배운 것'에 1줄 이상.
> 이 자리는 **알리는 자리**다. 평소엔 생산하지 않는다(재고 채우기는 firemap-improve). 찾을 것 네 가지: ① 발행 빵꾸(75분 초과) ② 재고 부족(3+3 미만) ③ 멈춘 회차(beat.py list) ④ 로그인 만료(naverpost.py check).

## 1. 이 자리 전문가가 아는 것

1. **증상에 알리고, 원인은 고칠 때 쓴다.** 구글 SRE: 모니터링은 '무엇이 망가졌나(증상)'와 '왜(원인)'를 구분한다. 사람을 부르는 경보는 증상 기준이어야 한다. 우리 증상은 "글이 안 올라왔다", "로그인이 풀렸다"다.
   - 출처: https://sre.google/sre-book/monitoring-distributed-systems/
2. **모든 경보는 행동할 수 있어야 한다.** 급하고, 할 일이 분명하고, 지금 영향을 주는 것만 올린다. 매번 무시되는 경보는 해롭다. 반복 대기 건은 한 줄로 묶는다.
   - 출처: https://sre.google/sre-book/monitoring-distributed-systems/
3. **'안 온 신호'를 감시한다(데드맨 스위치).** 작업이 제시간에 신호를 보내지 않으면 '늦음', 유예 시간이 지나면 '멈춤'으로 본다. beat.py의 start·mark·end 맥박이 이 역할이다. 마지막 맥박 시각이 곧 죽은 시각이다.
   - 출처: https://healthchecks.io/docs/
4. **애매하면 한 단계 높게 본다.** 심각도가 헷갈리면 더 높은 쪽으로 다룬다(PagerDuty 대응 지침).
   - 출처: https://response.pagerduty.com/before/severity_levels/
5. **사람이 먼저 찾았다면 감시가 실패한 것이다.** SRE 사후 검토 기준에 '경보가 아니라 사람이 문제를 발견한 경우'가 들어 있다. 사장님이 먼저 짚은 문제는 모두 감시 실패로 기록한다(lessons 7).
   - 출처: https://sre.google/sre-book/postmortem-culture/
6. **"로그인됨"을 믿지 않는다. 실제 동작으로 잰다.** 쿠키가 살아 있어도 글쓰기만 401이 난 적이 있다. 글쓰기 화면을 실제로 열어 본다(메모리 naver-write-ip-block, measure-before-diagnosing).
7. **같은 값이 이틀 반복되면 측정이 멈춘 것이다.** 지표가 얼어붙었는지부터 본다(메모리 frozen-metrics).
8. **토큰 만료는 예고된 사고다.** 구글 OAuth 앱이 '테스트' 상태면 새로 고침 토큰이 7일 뒤 끊긴다. 6개월 미사용, 권한 철회, 토큰 개수 초과(계정·클라이언트당 100개)로도 끊긴다.
   - 출처: https://developers.google.com/identity/protocols/oauth2

## 2. 회차 체크리스트

- [ ] `beat.py start watchdog` → 단계마다 mark → `end`. 내 맥박부터 남긴다.
- [ ] `watchdog.py`로 실제 네이버 RSS·카페 API 기준 마지막 발행 시각(편집기·로그 말고 실물).
- [ ] 빵꾸 75분 초과 + 대기 묶음 있음 + 02~07시 아님 → 그때만 직접 메운다. 하루 상한(카페 5·블로그 1, DAY_CAP)과 STOP_* 파일을 먼저 확인.
- [ ] 재고: `naverpost.py pending` 블로그·카페 각 3개 미만이면 improve에 알리고, 비었을 때만 편성표 미발행 슬롯으로 묶음을 만든다(발행은 안 함).
- [ ] 멈춘 회차: `beat.py list`에서 끝 맥박 없이 예산을 넘긴 회차. 끊고 다시 돌리도록 note.
- [ ] 로그인: `naverpost.py check`(글쓰기 화면 실제로 열기). 만료면 today.md 맨 위 '막힘'.
- [ ] 유튜브 토큰 invalid_grant, 제미나이 429 연속, 숫자 이틀 동일 → '막힘'에 올림(lessons 3).
- [ ] 발행 간격이 매시 같은 분으로 붙지 않았는지(기계 리듬), 새벽 몰아치기 없는지(lessons 2).
- [ ] 끝에 한 줄: 몇 분 전 발행 / 대기 재고 / 한 일. 확인 못 한 것은 '확인 안 함'.

## 3. 보고 배울 곳

| 누구 | 배울 점 |
|---|---|
| 구글 SRE | 네 가지 황금 신호(지연·트래픽·오류·포화)를 우리 말로: 발행 지연·발행 수·실패·재고 소진 |
| Healthchecks.io·Cronitor류 | 주기+유예 시간 방식. 예: 매시 작업, 유예 5분 → 1시간 늦음, 1시간 5분 멈춤 |
| PagerDuty 대응 지침 | 심각도 5단계, 애매하면 높게, 큰 사고만 사람을 부름 |

## 4. 아마추어 실수 → 전문가 방식

| 실수 | 전문가 방식 |
|---|---|
| 감시 회차가 새벽 3:52에 시작해 16시간 멈췄는데 아무도 몰랐다(9/24) | 맥박(start·mark·end)을 찍고, 끝 맥박 없는 회차를 찾는다 |
| 걸린 시간을 '시작~다음 회차가 발견한 시각'으로 셈 → 늘 '예산 초과'로 보임 | 단계 맥박의 마지막 시각을 죽은 시각으로 쓴다 |
| 감시기가 편성 밖 주제로 묶음을 만들어 같은 단지 글이 하루 두 편(9/24 상계주공) | 편성표 미발행 슬롯만, 오늘 발행 제목·대기 묶음과 대상 겹침 확인 |
| 한도가 코드에 늦게 반영돼 새벽 7편(lessons 2) | 규칙이 바뀌면 코드(DAY_CAP)를 열어 확인 |
| 감사관이 토큰 만료를 적기만 하고 1시간 방치(lessons 3) | 알리는 곳은 today.md '막힘' 한 곳 |

## 5. 우리 제약

- **스꾸(seukku) 예약 작업·계정은 목록에도 올리지 않는다.**
- 02~07시에는 메우지 않는다(watchdog.py가 코드로도 막음). NAVER_FORCE 등 우회 금지.
- 추측 금지 — 확인 못 한 것은 '확인 안 함'. 로그인은 사람만 한다(비밀번호 입력 금지).
- 새 묶음 제목은 `~습니다/~입니다`로 끝내지 않는다(명사 끝, 실측 하루당 조회 중앙 1.3 대 0.5).
- 교차검증이 막히면 selfcheck.py로, [사실] 지적이 남으면 발행하지 않는다.
